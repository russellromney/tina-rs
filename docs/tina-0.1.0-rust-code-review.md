# Tina/Tinio 0.1.0 Rust Code Review

**Date:** 2026-07-09

**Relationship to the launch review:** This is an additive, code-level pass over the findings in [`tina-0.1.0-ergonomics-correctness-review.md`](tina-0.1.0-ergonomics-correctness-review.md). It does not repeat the packaging, example coverage, or product-level API findings except where the literal Rust implementation adds useful evidence.

## Review lens

The review combined repository-specific inspection with:

- The [`rust-skills`](https://github.com/leonardomso/rust-skills) rule set, used selectively rather than as a blanket style mandate.
- The official [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html), [Clippy documentation](https://doc.rust-lang.org/clippy/), and Rust's [`unsafe` documentation](https://doc.rust-lang.org/std/keyword.unsafe.html).
- Rust-focused LLM research as a reason to distrust compilation as a completeness signal. Recent studies found recurring API hallucination and security/semantic errors in generated Rust even when code was intended to use Rust's safety model ([crate hallucination study](https://arxiv.org/abs/2606.08444), [cryptographic Rust study](https://arxiv.org/abs/2604.27001)). This review therefore looked specifically for ownership workarounds, swallowed errors, inaccurate unsafe contracts, unchecked arithmetic, and tests that encode an implementation accident as intended behavior.

These are review heuristics, not a claim that any particular Tina code was generated by an LLM.

## Findings

### P1: The framing codecs reject valid coalesced input

[`LengthDelimitedFramer::feed`](../tina-codec/src/length_delimited.rs) and [`LineFramer::feed`](../tina-codec/src/line.rs) cap the entire buffered chunk at one frame's maximum size. If a read contains one maximum-sized valid frame followed by any bytes from another valid frame, `feed` copies only the prefix of the chunk, marks the framer overflowed, and permanently drops the remainder. Because `feed` returns `()`, the caller cannot retain and resubmit the unconsumed bytes.

This was reproduced against the built crate:

```text
LengthDelimitedFramer(U8, max=4), input = [4, "abcd", 1, "x"]
=> Frame("abcd"), Full

LineFramer(max=4), input = "abcd\nx\n"
=> Frame("abcd"), Full
```

Both inputs contain two valid frames. Whether the second frame is accepted depends on transport chunking, which a codec must not expose as protocol semantics. The existing back-to-back tests use total input smaller than the single-frame cap, so they miss the boundary.

**Recommendation:** redesign feeding so boundedness applies to the current incomplete frame, not to an arbitrary socket-read chunk. A good first form is `feed(&[u8]) -> consumed_bytes`, with the caller alternating feed and drain; another is a decoder that accepts `&mut BytesMut` and advances only complete frames. Add property tests asserting that every partitioning and coalescing of the same valid byte stream produces the same frames. Avoid solving this with an unbounded internal queue of decoded frames.

The same rewrite should remove repeated front-of-`Vec` drains. [`next_frame`](../tina-codec/src/length_delimited.rs) and the line framer shift all trailing bytes after each frame; a cursor, `VecDeque`, or `BytesMut::split_to` avoids quadratic behavior for many coalesced frames.

### P1: Buffered HTTP/2 responses can deadlock above the initial window

[`Http2Connection::queue_or_send_response`](../tina-http/src/http2/server.rs) requires the complete buffered response body to fit both the connection and stream send windows before it emits any DATA. The source comment already describes the resulting deadlock: for a response larger than the initial roughly 64 KiB window, a conforming peer can wait for response bytes before returning WINDOW_UPDATE credit while Tina waits for enough credit to send the whole response.

This is protocol behavior, not only a performance limitation. It affects ordinary buffered responses; the separate streaming response path already contains the right incremental shape.

**Recommendation:** send HEADERS immediately, retain a body cursor, emit DATA up to the minimum of peer frame size and currently available stream/connection credit, and resume on WINDOW_UPDATE. Reuse the streaming response pacer rather than maintaining two flow-control implementations. Add a live test with a default-window peer and a buffered response larger than 65,535 bytes where the peer only credits bytes after receiving them.

Also remove the unchecked `p.body.len() as i32` in `flush_pending_responses`. The earlier path uses `i32::try_from`, but the later retry path reintroduces a wrapping conversion.

### P1: Public durations can panic through unchecked `Instant` addition

Tina already has a careful saturating implementation in [`Deadline::from_instant`](../tina/src/context.rs). Several runtime and bridge paths bypass it and use `Instant + Duration`, which panics when the configured duration is not representable:

- Raw sleeps in [`BetelgeuseDriver::submit`](../tina-runtime/src/driver/mod.rs).
- DNS and TLS operation deadlines in [`driver/dns.rs`](../tina-runtime/src/driver/dns.rs) and [`driver/tls.rs`](../tina-runtime/src/driver/tls.rs).
- Threaded shutdown deadlines in [`threaded.rs`](../tina-runtime/src/threaded.rs) and [`threaded_multi_shard.rs`](../tina-runtime/src/threaded_multi_shard.rs).
- Reqwest retry scheduling in [`tina-reqwest-bridge/src/worker.rs`](../tina-reqwest-bridge/src/worker.rs).
- Several observer, host-burst, HTTP keepalive, Tokio bridge, and AWS bridge waits.

These durations are supplied through public effects or configuration. `Duration::MAX` should not unwind a shard or constructor, and different debug/release behavior is particularly undesirable in a deterministic runtime.

**Recommendation:** centralize deadline arithmetic around one checked policy. Either return a typed `DurationOutOfRange` at configuration/effect admission or consistently saturate through `Deadline`. Add boundary tests using `Duration::MAX` for every public timeout family. Use explicit checked, saturating, or wrapping arithmetic for timer ordinals and other sequence counters as well; `next_timer_ordinal += 1` currently has debug-panic/release-wrap semantics.

### P1: The Tokio RPC bridge returns a non-`Send` call future

Pedantic/nursery Clippy reports `future_not_send` for [`BridgeClient::call`](../tina-rpc-tokio/src/lib.rs). `BridgeClientInner<S>` contains `PhantomData<S>`, so auto-traits act as though the bridge owns an `S`. The implementation only carries shard-typed addresses and does not store an `S`; holding `&self` across the oneshot await therefore unnecessarily requires `S: Sync`.

This matters at the intended boundary: a Tokio-facing client call should be spawnable with `tokio::spawn`. Direct `.await` tests do not catch that requirement.

**Recommendation:** express the actual relationship with a non-owning marker such as `PhantomData<fn() -> S>` if that matches the intended variance, or remove the generic marker from the inner type. Add compile-time assertions that `BridgeClient<S>: Send + Sync` and that `BridgeClient::call(...)` produces a `Send` future for an ordinary shard type. Do not add `S: Sync` merely to suppress the symptom unless the bridge really shares an `S`.

### P1: `unsafe` is used to enforce non-safety policy

Two public internal surfaces explicitly say their unsafety is "not for memory safety":

- [`request_effect_from_consumed_effect`](../tina/src/lib.rs) uses `unsafe` to mark an opt-out from must-answer request authority.
- Pool ID/resource/lease constructors in [`tina/src/pool.rs`](../tina/src/pool.rs) use `unsafe` to discourage forging logical pool identity.

Rust's unsafe boundary is a proof boundary for soundness: safe callers must not be able to cause undefined behavior. It is not a general-purpose visibility modifier or an annotation for business-logic invariants. Using it for non-safety policy makes `unsafe` audits noisier, conflates `#![forbid(unsafe_code)]` with product-policy enforcement, and teaches contributors the wrong contract.

**Recommendation:** replace these with a real crate boundary, sealed capability/token, or a small shared internal crate that owns the constructors. If the pool contract can genuinely lead to Rust undefined behavior, document the exact safe API and unsafe operation that relies on it; otherwise make it safe-but-hidden and enforce misuse through privacy and types. The must-answer escape hatch can be a deliberately named `runtime_internal` capability without claiming a memory-safety obligation.

### P1: The actual unsafe substrate lacks a mechanically enforced audit standard

A targeted run of:

```sh
cargo clippy --workspace --lib -- \
  -W clippy::undocumented_unsafe_blocks \
  -W clippy::missing_safety_doc
```

reported 110 undocumented unsafe blocks in the customized vendored Betelgeuse crate on the current macOS target. It also found undocumented blocks in Tina's process/pool code and three in `tina-mailbox-spsc`. Linux-only affinity code was not compiled by that run and contains additional raw libc calls that need the same review.

The SPSC mailbox is substantially better than the vendor substrate: it documents its invariants, uses Loom, denies `unsafe_op_in_unsafe_fn`, and keeps unsafe operations local. Its `// Safety:` comments are not attached closely enough to each cfg-specific unsafe block for Clippy to recognize them; converting them to immediate `// SAFETY:` proof comments is a small fix.

**Recommendation:** make `clippy::undocumented_unsafe_blocks` and `unsafe_op_in_unsafe_fn` denied lints in every crate that permits unsafe. Audit the vendored completion-pointer casts, slab access, kqueue operations, socket address casts, and simulated backend first. Run the unsafe lint on Linux and macOS; use Miri for the platform-independent completion/slab/simulated code and retain Loom for the SPSC memory-ordering model. Comments are not proof, but requiring the intended invariant makes review possible.

### P2: Write-all helpers clone and shift their full remaining buffers

[`TcpWriteAll`](../tina-runtime/src/tcp_loops.rs), [`UnixWriteAll`](../tina-runtime/src/unix_loops.rs), and [`FileWriteAll`](../tina-runtime/src/file_loops.rs) clone the entire pending `Vec<u8>` for each issued write, then `drain(..count)` from the front after partial progress. The file-copy pump clones its in-flight buffer the same way.

Under repeated short writes this performs repeated allocations/copies plus repeated left shifts. It can approach quadratic byte movement while temporarily retaining two copies of the payload. This is exactly the ownership workaround that deserves scrutiny in Rust: cloning made the borrow/move problem easy but defeated the runtime's bounded-memory and native-I/O goals.

Tina already has `tcp_write_owned`, whose completion returns the buffer. The helper does not use it.

**Recommendation:** make the owned-buffer rail the default for write loops, store a cursor/range instead of draining the front, and add owned-buffer variants for Unix/file writes. The state machine should move one allocation into the driver and receive it back on every completion. Benchmark forced one-byte partial writes and assert allocation count as well as bytes copied.

The current `count.min(pending.len())` handling also hides an impossible backend result. A completion claiming more bytes than submitted should surface an internal/protocol invariant failure, not silently clamp and report success.

### P2: `try_header` silently discards the error

[`RequestBuilder::try_header`](../tina-http/src/request_builder.rs) returns `Self`, and invalid input leaves the builder unchanged. Its unit test is named `try_header_swallows_invalid` and locks in that behavior.

This is surprising Rust API design: a `try_` method implies visible failure, while silent omission can produce a request with missing authentication, content negotiation, tracing, or integrity metadata. The caller cannot distinguish insertion from rejection.

**Recommendation:** return `Result<Self, InvalidHeader>` and preserve whether the name or value failed. Keep a separate explicitly named best-effort helper only if there is a demonstrated use case. Consider making the ordinary `header` method fallible and offering a static/prevalidated fast path for literals.

### P2: Fallible constructors mix `Result` with hidden panics

The launch review already recommends fallible runtime construction. The code-level pass found the same issue in APIs that already return `Result`. [`BridgeClient::new`](../tina-rpc-tokio/src/lib.rs) asserts both capacity relations and `expect`s checked addition before returning `Result<Self, BridgeError>`. Callers reasonably expect all validation failures to arrive through `BridgeError`.

**Recommendation:** validate every caller-controlled field into the declared error type. Use `NonZeroUsize` or validated configuration types when zero is never meaningful. Reserve panics for internal invariant violations, document them with `# Panics`, and do not combine validation `Result`s with assertion-based validation in the same constructor.

### P2: Install errors erase their source chains

Bridge installation frequently converts structured errors to strings, for example SQLx runtime/pool/register failures in [`tina-sqlx-bridge/src/worker.rs`](../tina-sqlx-bridge/src/worker.rs), SQLite open/setup/spawn failures, and AWS/reqwest setup errors. The public error enums then implement `Error` without returning a source.

String transport may be justified for errors crossing isolate or replay boundaries, but installation occurs locally and benefits from source inspection, downcasting, and complete diagnostics.

**Recommendation:** retain concrete source errors in install-time variants (or boxed `dyn Error + Send + Sync`) and implement `source()`. Convert to stable typed classifications plus diagnostic strings only at the runtime message boundary where determinism or cloneability requires it.

### P2: A never-type implementation triggers an undefined-behavior lint

[`IntoSendErasedSpawn::mailbox_capacity`](../tina-runtime/src/dispatch.rs) for `Infallible` uses `match *self {}`. Clippy's `uninhabited_references` lint reports that dereferencing a reference to an uninhabited type is undefined behavior.

The method is unreachable in well-formed safe code, but there is no value in encoding the impossible branch with an operation the compiler identifies as UB.

**Recommendation:** use a safe explicit `unreachable!` path with a precise invariant message, or restructure the trait so the by-reference method does not need an `Infallible` implementation. Enable `clippy::uninhabited_references` in CI.

### P2: Narrowing conversions need either validation or a target policy

The code generally handles wire-size conversions carefully, but some public/persistent paths still use unchecked narrowing:

- Snapshot and journal decoders cast an untrusted `u64` payload length to `usize` in [`persistence.rs`](../tina-runtime/src/persistence.rs). On a 32-bit target, a malformed large length can truncate to a small accepted length.
- Worker-pool capacities and waiter indexes are `usize` but are stored through `as u32` in [`pool.rs`](../tina-runtime/src/pool.rs).
- Several HTTP report and flow-control values narrow with `as` after validation in a different function, making the invariant non-local.

**Recommendation:** use `TryFrom` at the boundary and return the existing corrupt/configuration error on failure. If Tina only supports 64-bit platforms, state and enforce that target policy explicitly in build configuration and documentation rather than relying on it implicitly.

### P2: The public API needs selective evolution guards and `must_use`

The workspace is strong on `missing_docs`, but it has no workspace lint policy and relatively sparse `#[must_use]` coverage. A pedantic/nursery Clippy run reported 244 `return_self_not_must_use` warnings, including routers, request builders, local-system builders, and trace timeline builders. Ignoring one of these consuming builder calls silently discards the configured value.

Likewise, many externally matched outcome/error enums are exhaustive today. Some are probably intentionally closed, but types such as `CallRejectedReason` are likely to grow as the runtime adds terminal causes. This decision should be made before 0.1 rather than accidentally through omission.

**Recommendation:**

- Mark consuming builder types or every `self -> Self` method `#[must_use]`.
- Inventory public error, outcome, report, and configuration types; apply `#[non_exhaustive]` where future variants/fields are expected, not indiscriminately to application message enums.
- Add workspace lints and inherit them with `[lints] workspace = true` in every crate. Start with high-signal rules: `unsafe_op_in_unsafe_fn`, `clippy::undocumented_unsafe_blocks`, `clippy::uninhabited_references`, `clippy::return_self_not_must_use`, selected narrowing-cast lints, and explicit allowances with reasons.
- Keep full `clippy::pedantic` and `clippy::nursery` advisory. The review run produced thousands of low-signal style suggestions, so denying those groups wholesale would obscure the correctness lints.

## Positive Rust patterns to preserve

The code already contains several patterns that coding agents often fail to produce without strong direction:

- Request authority is encoded through consuming types rather than runtime booleans.
- Most queues and admission surfaces have explicit capacity and typed refusal.
- Newtype IDs prevent accidental cross-domain integer mixing.
- Owned TCP read/write rails return buffers on both success and failure.
- `Deadline` uses checked arithmetic and documents overflow policy.
- The SPSC mailbox states its invariants and has Loom/Miri-oriented tests.
- Protocol parsers usually validate announced sizes before allocating and use checked length addition.
- Cancellation and late completion are modeled as outcomes rather than dropped tasks.

The improvements above should extend those existing design instincts to the remaining literal code, not replace them with broad abstractions or mechanical Clippy cleanup.

## Recommended implementation order

1. Fix codec chunking invariance and add partition/coalescing property tests.
2. Pace buffered HTTP/2 responses through available flow-control credit.
3. Centralize checked deadline arithmetic and test hostile durations.
4. Make the Tokio RPC call future `Send` and add compile assertions.
5. Separate logical capability restrictions from actual Rust unsafety; then audit and lint the remaining unsafe substrate.
6. Convert write loops to owned buffers plus cursors.
7. Correct `try_header`, mixed panic/`Result` constructors, and install error chains.
8. Add selective workspace lints, `must_use`, non-exhaustive decisions, and checked narrowing.
